## The improvement in one line

**Links to this site now show an image preview when shared on WhatsApp,
LinkedIn or any other platform.** They previously showed text only.

---

## The problem found

Every one of the 18 pages contained this in its `<head>`:

```html
<meta name="twitter:card" content="summary_large_image">
<meta property="og:title"       content="...">
<meta property="og:description" content="...">
                            <!--  no og:image anywhere  -->
```

The first line asks sharing platforms for a **large image preview**. No image
was ever supplied, so the request went unanswered.

Verified before starting:

```
$ grep -l 'og:image' *.html
(no output — none of the 18 pages had it)

$ ls -A assets/img/og/
.gitkeep          (the folder was empty)
```

**Real-world effect,** confirmed by pasting a product link into WhatsApp: the
preview showed the product title, the description and the domain — but an
**empty grey space where the photograph should be.**

This matters for this site specifically. Panwar Knitwear is a B2B wholesale
manufacturer: enquiries arrive because distributors forward links to each
other on WhatsApp. A preview with no product photo is the difference between
a link that gets tapped and one that gets ignored.

The gap was already logged in `docs/CONTENT-TODO.md` §2 as outstanding.

## The fix

### 1. Product pages (12 files) — no new assets needed

Each product page already displayed an 800×800 photograph. That same file
became its `og:image`, so sharing a product link now previews *that product*:

| Page | Preview image |
|---|---|
| `product-zonixa-hoodie-logo.html` | `zonixa-hoodie-logo.jpg` |
| `product-zonixa-winter.html` | `zonixa-winter.jpg` |
| `product-msp-capri.html` | `msp-capri.jpg` |
| …and 9 more, each using its own photo | |

### 2. The other 6 pages — one shared card

`index`, `zonixa`, `msp-sports`, `about`, `contact` and `404` share a new
**1200×630** card at `assets/img/og/og-default.jpg`.

Built only from assets already in the project, so nothing is invented:

- `--clr-ink-900` (`#0d0f12`) ground — the site's own dark-section colour
- the knit-stitch texture from `assets/svg/pattern-knit.svg`, as the hero uses
- the verified company name, brand names and location

Generated by **`tools/make-og-image.ps1`**, committed so the card is
reproducible rather than an unexplained binary. It uses .NET `System.Drawing`
because Node.js is not installed on the development machine — the same
constraint that shaped the whole project (see `README.md`, "Why no framework").

### 3. Absolute URLs — the detail that makes it work

`og:image` **must be an absolute URL**; crawlers ignore relative paths. The
base matches the existing `og:url` and `canonical` tags:

```html
<meta property="og:image" content="https://panwarknitwear.com/assets/img/zonixa/zonixa-winter.jpg">
<meta property="og:image:alt" content="Zonixa winter hoodies with chest prints, shown in seven colourways">
```

`og:image:alt` was added alongside — it is what a screen reader announces for
the preview card, consistent with the accessibility rules in `CLAUDE.md`.

### 4. A regression guard

`tools/verify.ps1` previously read only **2 of the 18 pages**
(`index.html` and `contact.html`) — which is precisely why this defect went
unnoticed. It now loops every page and asserts four things:

| Check | Catches |
|---|---|
| every page with `twitter:card` has `og:image` | the original defect |
| every `og:image` is an absolute URL | relative paths crawlers ignore |
| every `og:image` resolves to a file on disk | typos and renamed images |
| every `og:image` has `og:image:alt` | missing accessible description |

**The guard was tested by deliberately reintroducing the bug** three ways —
removing the tag, making it relative, and pointing it at a missing file. Each
was caught, then the page was restored. A check that can only pass is worthless.

## Known limitation

The `og:image` URLs use `https://panwarknitwear.com/`, matching the existing
`og:url` and `canonical` tags in the Homework 2 baseline.

**If the site is shared from a different domain** (for example a
`*.vercel.app` address), those three tags must be updated together or the
preview image will not load. This is a one-line-per-page change and is
deliberately left as-is so all URL tags stay internally consistent.

## Deliberately out of scope

Other issues were found while investigating and left for future work, since
the task was one small improvement:

- **`msp-sports.html` contradicts itself** — its `<title>` promises "Track
  Pants, Lowers & Shorts" and its description lists six categories including
  Sportswear, but the page shows five cards named "Product 1–5"; a feature
  reads "Six length options" above text listing four.
- **`assets/js/products.js` is loaded by no page** — 288 lines whose header
  claims `product-page.js` renders it, but no such file exists. It holds a
  duplicate of all product data that already disagrees with the shipped pages.
- **Product pages are dead ends** — no prev/next or related-products link, so
  comparing products means returning to the listing each time.
- **"Send an enquiry" loses the product** — it lands on a blank form, so the
  manufacturer cannot tell which of 12 styles an enquiry concerns.
- **12 hard-coded phone numbers** on product pages bypass the
  `site.config.js` single-source-of-truth, and point at the *secondary* line
  while each page's own footer points at the primary.
